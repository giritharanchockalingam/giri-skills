# Performance rules PF1–PF10

Static rules implemented in `scripts/perf_review.py`. Each has an id, what the scanner matches, why it matters under load, the fix, and the cases it deliberately does not flag. Severity is **high** when the cost grows with data volume or request count without bound (one bad deploy takes the site down at peak) and **medium** when the cost is real but bounded (slower, heavier, but it stays up).

| Id | Name | Severity | Matches | Why it matters | Fix |
|---|---|---|---|---|---|
| PF1 | n-plus-one-query | high | Supabase `.from(`/`.rpc(` or `fetch(` inside a `for`/`while` body or inside a `.map(`/`.forEach(`/`.flatMap(` callback | One round trip per row: 500 rows → 500 queries; latency and connection use scale with the list, and PostgREST/pooler limits are hit first at peak | One query with `.in("fk", ids)`, an embedded select (`select("id, items(sku, qty)")`), or one RPC; then join in memory |
| PF2 | await-in-loop | medium | `await` inside a `for`/`while` body that is not a `for await` loop and is not already a PF1 line | Independent async work runs one after another; total time is the sum instead of the max | Build the promise array and `await Promise.all(...)` (or `Promise.allSettled`); keep a loop only when order or back-pressure is required and say so in a comment |
| PF3 | select-star | high | `.select("*")`, or a select list whose top-level columns include `*` or an embedded `rel(*)` | Every column crosses the wire and is serialised, covering indexes cannot be used, and a later wide column (JSON, text) silently inflates every response | Name the columns the page renders; keep `*` out of embedded selects too |
| PF4 | unbounded-list-read | high | A `.from(…).select(…)` read chain with no `.limit(`, `.range(`, `.single(`, `.maybeSingle(`; writes (`insert/update/delete/upsert`), `head: true` counts and `.eq("id", …)` point reads are exempt | Response size and query time grow with the table; the page that was fine at 2k rows times out at 200k | Paginate with `.range(from, to)` from `searchParams`, or cap with `.limit(n)` and expose "load more" |
| PF5 | fetch-in-use-effect | medium | In a `"use client"` file, a `useEffect(` whose callback body calls `fetch(`, `.from(` or `.rpc(` | The request starts only after hydration: HTML → JS → render → fetch → re-render, a waterfall that doubles time-to-data and bypasses the server cache | Fetch in the server component (page or a server parent) and pass data as props; for client-only interactivity use a server action or a cached route |
| PF6 | heavy-compute-in-render | medium | In a `"use client"` PascalCase component body, `.sort(` or `.filter(` on a destructured prop or `props.x` outside `useMemo`/`useCallback`/`useEffect` | The derived list is recomputed on every render (every keystroke, every parent re-render); sort is O(n log n) and allocates a new array, which also defeats memoised children | `useMemo(() => orders.filter(...).sort(...), [orders, query])`; for very large lists move the sort to the query |
| PF7 | img-instead-of-next-image | medium | `<img` in a `.tsx`/`.jsx` file | No resizing, no modern formats, no lazy loading, no size reservation: large transfers and layout shift (LCP, CLS) | `import Image from "next/image"` with `width`/`height` (or `fill`) and `sizes`; add the remote host to `images.remotePatterns` |
| PF8 | heavy-import-in-page | medium | In `app/**/page.*` or `layout.*`, a static `import … from` one of: recharts, chart.js, react-chartjs-2, plotly.js, react-plotly.js, d3, three, @react-three/fiber, monaco-editor, @monaco-editor/react, codemirror, @codemirror/view, mapbox-gl, leaflet, react-leaflet, pdfjs-dist, react-pdf, jspdf, html2canvas, xlsx, quill, react-quill, @tiptap/react, ag-grid-react, @fullcalendar/react, moment, lodash | The whole library lands in the route's bundle (and a layout's import lands in every route under it), paid on first load even when the widget is below the fold or behind a tab | `const Chart = dynamic(() => import("@/components/charts/RevenueChart"), { ssr: false })` from the page; keep the heavy import inside the client component |
| PF9 | no-store-on-every-fetch | medium | A server page (`app/**/page.*` without `"use client"`) with at least one `fetch(` where every call passes `cache: "no-store"` | The page is fully dynamic: every request re-fetches upstream; no ISR, no CDN hit, upstream rate limits reached first under a spike | `fetch(url, { next: { revalidate: 60 } })` or `next: { tags: [...] }` with `revalidateTag` on write; keep `no-store` only for the one truly per-user call |
| PF10 | sync-fs-read-in-handler | medium | In `app/**/route.*`, `readFileSync(`/`readdirSync(` inside an exported `GET|POST|PUT|PATCH|DELETE|HEAD|OPTIONS` body; module-scope reads are not flagged | The read and the `JSON.parse` run on every request and block the event loop for the whole process | Read and parse once at module scope (cached for the process), or move the data to the database / a KV store |

## Gate
- Exit 1 when any high finding is **new**; exit 0 otherwise. Outputs are always written.
- `--baseline findings.csv`: a finding whose rule, file and snippet match a baseline row is `known` (line numbers may move); unmatched baseline rows are reported as resolved. Known highs do not gate — they are recorded debt with their own PRs.

## Known false positives and limits (say these plainly in a review)
- Static text matching, not a type-checked AST: a `.from(` on a non-Supabase object (e.g. `Array.from(`) is not matched because the scanner requires a string literal argument, but a custom query builder with the same method names is treated as Supabase.
- PF1 also fires on `Promise.all(ids.map(id => supabase.from(...)))` — parallel, but still N queries; the fix is the same (`.in()`), so it stays high.
- PF2 flags a loop that is intentionally sequential (rate-limited upstream, ordered writes). Keep the loop and record it in the baseline with the reason in a code comment.
- PF4 cannot see RLS or a unique filter other than `.eq("id", …)`; a read bounded by a unique business key (`.eq("slug", …)`) without `.single()` is flagged — add `.maybeSingle()`, which is also the correct type.
- PF6 only inspects PascalCase components with parenthesised parameters in `"use client"` files and only `.sort(`/`.filter(` chains whose receiver is a prop; a local `useState` array that is sorted in the body is not flagged (conservative by design).
- PF8's library list is fixed (above); add your own heavy packages by extending `HEAVY_LIBS` in the script and this table together.
- PF9 reads `fetch` options literally; a `no-store` set through a wrapper function or `export const dynamic = "force-dynamic"` is not seen.
- Nothing is executed or measured: no bundle sizes, no query plans, no latency. Use `observability-setup` for production numbers and confirm each fix with them.
